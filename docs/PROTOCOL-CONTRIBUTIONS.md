# 协议贡献与证据约定

本项目使用原生客户端进行本地兼容测试。协议贡献的目标是解释可复算的行为、保护现有状态并形成可验证实现，不是把未知字节填成看似可用的值。通用协作约定见 [CONTRIBUTING](../CONTRIBUTING.md)。

## 一项贡献应包含的内容

| 项目 | 需要记录 |
| --- | --- |
| 目标 | 客户端版本、EXE的 SHA-256、相关资源版本；不要只写“最新版”。 |
| 请求 | 方向、消息编号、完整帧长度、载荷长度、头部规则及触发操作。 |
| 字段 | 相对完整帧还是载荷的偏移、宽度、符号、字节序、单位及条件分支。 |
| 状态 | 权威来源、归属、生命周期、失败与重复请求的行为。 |
| 回复 | 成功、拒绝及状态同步分别使用哪些消息；出现某个编号不自动等于成功。 |
| 依据 | 代码检查、静态消费者、实际 TCP、客户端实测分别说明，列出尚未闭合的环节。 |
| 验证 | 合成输入、边界、预览／提交、失败不修改、重启与重复处理结果。 |

不能提交原版二进制、原始客户端资源、原始抓包、真实账号帧或存档。公共说明只保留必要的字段事实和自己编写的最小示例；第三方资料的权利不由本仓库许可覆盖。

## 区分三种证据

**静态消费者**可以证明某版本读取哪些字节、走哪个分支、写哪个缓存。记录目标 SHA与有限范围的地址或可复算定位方法；地址只适用于该目标。静态分析没有观察运行时实际状态，也不是用户画面验收。

**原生 TCP测试**可以证明服务实际收发、序列化、事务与保存行为。需要等待实际应答和事件，不能用固定短延时掩盖竞态。测试必须在独立目录与端口运行，不写玩家现有数据。

**客户端实测**可以证明对应版本、场景和操作下的显示与交互。它不能单独证明概率精确、所有异常分支或全部英雄都通过。报告应保留具体范围，不把一次通过扩大为全量还原。

结论分别标为已观察、由证据推导或未知。新证据推翻解释时更新结论，并说明影响的代码与测试；不要抹去失败或把推测改写成直接观察。

## 当前容易误用的合同

### 邮件的读、领与保护初始化

- C2S20306载荷为4字节邮件 ID，用于请求详情并标为已读；已读不等于已领取。
- C2S20305完整帧为17字节，载荷为4字节无符号邮件 ID和尾部字节5。邮件 ID不能随意收窄为有符号整数；分页显示 ID需正确映射回所属邮件。
- 领取必须验证归属、附件、容量及现有领取状态，失败不能发奖励，已领取不能重复授予。详情或附件图标的出现不证明奖励提交成功。
- 公共账号初始化补充的 S2C20419完整帧为14字节，正文为两字节零。已核对的客户端分派直接清除本地保护锁，未读取这两个字节，不能把它们命名为已经证明的“成功状态码”。这项初始化不替代服务端资产校验，也不新增通用解锁／领奖接口。

若界面点击没有进入预期请求，先检查实际请求及原生前置门控。不能仅凭高位 ID、已读图标或截图猜测根因。

### 符文的界面门控与状态

9027功能列表控制原生界面的部分入口。当前公共初始化仅打开已确认的许愿／保底与批量强化入口；不能复制其他来源的整份功能表，或为显示按钮开启未核对功能。

S2C11855完整帧为40字节，七个 DWORD依次为：

```text
status, smallPity, regularWishId, regularLargePity,
limitedWishId, limitedLargePity, isLimited
```

常驻和限定状态应来自当前存档。后两状态槽不是保底上限；已核对客户端从自身配置读取上限。登录、重登与后续回复都不能用旧模板覆盖玩家当前许愿与保底。

### 批量强化是连续单次请求

C2S11681完整帧为29字节：四个无符号32位实例 ID和一字节模式，置于通常的12字节头后。模式1为预览，模式0为提交；预览不扣料，提交按一次操作处理。原生客户端负责批量面板的开始、停止与循环，不应另造服务端批量包。

测试至少覆盖两组连续操作、预览不修改、只消耗选中材料、未选实例与已配置页不变，以及正常保存重启。相同载荷未必是网络重试，不能凭内容哈希一律去重；反过来，明确已有事务身份的 GM操作也不能重复授予。

### 宝石一键摘除

原生按钮连续提交同方案、同装备的0至3孔摘除请求；单孔请求中的固定尾字节不是新造的“全部摘除”标记。完整序列才触发当前装备的原子全摘规划，序列中断、超时、断开、容量不足和重复空盘都需要保持既有语义。不要把当前装备全摘扩展成其他装备或方案全摘。

### 固定布局与战场名单

23512身份帧固定39字节，姓名使用固定字段并补零；不能按字符串长度缩短整帧，也不能要求短姓名的首个零必须恰好在整包末尾。

战场加载涉及23435、23505、23444、23560多张表。它们必须使用一致的当前 actor及槽位，不能只修改最后一张名单。未入场信息、视野中的配装和最终参战结果有不同边界，不能靠伪造身份字段或泄露未来状态修复显示。

## 有意义的测试边界

- 数值：零、上限、溢出、无符号高位、无效枚举与未知标志；货币沿用现有整数单位。
- 传输：拆包、粘包、合法封装、断开和实际应答；完整帧长度与载荷长度分开断言。
- 业务：预览不修改、拒绝不扣除、容量不足、归属错误、重复领取、另一账号不变。
- 生命周期：登录／重登、进出场、死亡复活、控制中断、已发射与未发射弹道、正常保存重启。
- 来源：资料缺失或版本不匹配应明确拒绝；不能为通过检查删除来源、身份、路径、租约或 pending校验。

测试应使用虚拟账号、虚拟实例和明确合成帧。示例中的编号必须说明是协议编号还是虚拟业务数据，禁止照抄真实账号 ID、GUID、认证字段或整段原始载荷。

## 提交检查

提交前说明具体改变了哪个原生合同、影响哪些业务、采用什么证据，以及仍待什么验证。把实现、必要测试与文档一并提交；测试数量本身不是完成度。

构建与封装变化还需在新输出目录验证实际产物。涉及客户端配置、保护规则或持久化的更改，应证明可恢复、冲突不覆盖、只操作本工具拥有的目标。协议贡献不会自动授权运行平台／更新器、修改真实存档或扩大项目范围。
